## Подготовка mock

Команды выполняются из корня репозитория с Node.js 20+:

```sh
npm --prefix mobile-engineer-kit run fixtures:oversize
npm --prefix mobile-engineer-kit start
```

Сервер работает в этом терминале. В другом терминале проверить доступность и выбрать режим:

```sh
curl --fail-with-body http://127.0.0.1:8787/health
curl --fail-with-body -X POST http://127.0.0.1:8787/__test/scenario \
  -H 'Content-Type: application/json' -d '{"mode":"happy"}'
curl --fail-with-body http://127.0.0.1:8787/__test/state
```

Для Android-эмулятора:

```sh
adb reverse tcp:8787 tcp:8787
```

Сброс ниже **удаляет локальное синтетическое состояние mock**: jobs, ключи и счётчики. Он не очищает состояние клиента. Использовать между независимыми прогонами после сохранения доказательств; не сбрасывать mock в середине проверки relaunch или retry.

```sh
curl --fail-with-body -X POST http://127.0.0.1:8787/__test/reset
```

Новый независимый прогон требует согласованного исходного состояния клиента и mock. Удаление данных клиента нельзя использовать вместо доказательства корректного восстановления операции.

## Основные сценарии

Найденные при сверке 2026-11-02 доработки закрыты: `queued` и `processing` имеют разные подписи, после сохранённого однозначного отказа первого POST с 413/415 доступен выбор другого файла. Неизвестный сетевой исход, старые записи и отказ после неоднозначной предыдущей попытки не разрешают сброс операции. Проверки этого этапа приведены в конце документа.

В чистом mock `newJobs=1`, `acceptedBytes>0`. | Ручной прогон подтверждён кандидатом 2026-11-03; отдельные счётчики этого файла не зафиксированы инструментально |

Сценарии переключаются без изменения исходников:

```sh
curl --fail-with-body -X POST http://127.0.0.1:8787/__test/scenario \
  -H 'Content-Type: application/json' -d '{"mode":"lost_ack"}'
curl --fail-with-body -X POST http://127.0.0.1:8787/__test/scenario \
  -H 'Content-Type: application/json' -d '{"mode":"stale_status"}'
curl --fail-with-body -X POST http://127.0.0.1:8787/__test/scenario \
  -H 'Content-Type: application/json' -d '{"mode":"delete_failure"}'
curl --fail-with-body -X POST http://127.0.0.1:8787/__test/scenario \
  -H 'Content-Type: application/json' -d '{"mode":"happy"}'
```

Выполнять только команду нужного режима перед соответствующим прогоном. Возврат в `happy` для повторного удаления выполняется **без reset**.

Для сравнения счётчиков до и после локального отклонения файла можно сохранить ответы в отдельные временные файлы:

```sh
curl --fail-with-body http://127.0.0.1:8787/__test/state > /tmp/import-state-before.json
# Здесь выбрать плохой файл в приложении и дождаться локальной ошибки.
curl --fail-with-body http://127.0.0.1:8787/__test/state > /tmp/import-state-after.json
```

Сравнить поле `stats.createRequests`. При `lost_ack` проверять `stats.newJobs`, а не требовать ровно один HTTP-запрос: идемпотентный retry допустим.

### iOS: подтверждение, 503, перезапуск и повтор

Проверена ранее созданная синтетическая операция `job-demo-001` на iPhone 16 Plus / iOS 18.2. Между ошибкой и повтором mock не сбрасывался.

1. «Удалить импорт» открыл подтверждение. «Оставить импорт» закрыл его: `deleteRequests=0`, `deleteKey` в журнале отсутствовал, результат оставался ready.
2. В режиме `delete_failure` подтверждение отправило DELETE. Интерфейс показал «Удаление не завершено» и «Повторить удаление», результат скрыт. Сервер сохранил ready; `deleteRequests=1`. Отдельный ключ удаления остался в журнале. Скриншот: `/tmp/statement-delete-ios-error.png`.
3. После `simctl terminate` и повторного открытия ключ сохранился. GET проверил состояние, но автоматического DELETE не было: счётчик остался 1.
4. Mock переключён в `happy` без reset. «Повторить удаление» использовал прежний ключ. Сначала отображалось «Удаляем импорт…», после GET — «Импорт удалён» и кнопка новой выписки. В state mock проверено соответствие сохранённого ключа исходному job ID.
5. На завершении этого прогона: `deleteRequests=2` (один неуспешный, один успешный), `createRequests=1`, `newJobs=1`, job — deleted. В каталоге операции остался только `{version:1,cleared:true}`, обе cache-папки пусты/отсутствуют, исходная фикстура сохранена. Скриншот: `/tmp/statement-delete-ios-complete.png`.

После проверки в iOS появилась отдельная новая операция `job-demo-002`, ready; исходная `job-demo-001` осталась deleted. Автоматизированные действия в новой операции не выполнялись. Полная цепочка её выбора и подтверждения не наблюдалась и отдельно не засчитывается.

- `npm run typecheck` — успешно; `npm run test:mobile` — **86/86**, лог `/tmp/statement-rejection-client-tests.log`.
