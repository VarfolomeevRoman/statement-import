# Импорт, восстановление и удаление

В фиче `statement-import` реализован путь от подтверждения файла до результата, восстановление после потерянного ответа, серверное удаление с повтором и начало следующего импорта после очистки. Реализация и автоматические проверки не заменяют нативную приёмку: результаты iOS и Android фиксируются отдельно в [матрице приёмки](acceptance.md).

## Пользовательский сценарий

1. Выбрать синтетический PDF или CSV через системный диалог. Приложение показывает имя, размер и формат; файл ещё не отправлен.
2. Нажать «Подтвердить и отправить». До сетевого запроса приложение создаёт постоянную собственную копию и сохраняет операцию со случайным ключом.
3. Дождаться обработки. Ответ POST означает только принятие запроса; результат приложение получает отдельным GET.
4. Просмотреть регулярные списания и раскрыть подробности позиции. Для фикстур mock возвращает StreamBeam — 19,99 AUD и BrightGrid — 132,00 AUD в месяц, всего 151,99 AUD. Сумма вычисляется из ответа, а не подставляется в UI.
5. Если ответ потерян, приложение ищет существующий импорт. При неудачной проверке доступно «Повторить»; повторная передача, если она нужна, использует прежние ключ и байты.
6. Нажать «Удалить импорт» и подтвердить удаление. «Оставить импорт» закрывает подтверждение без запроса. После отправки удаления результат скрывается; приложение ждёт подтверждения сервера. При ошибке доступно «Повторить удаление».
7. После серверного подтверждения и локальной очистки появляется «Импорт удалён». Кнопка «Выбрать новую выписку» возвращает к выбору файла; новый импорт получает новый ключ.

`queued` отображается как «В очереди…», `processing` — как «Обрабатываем выписку…». Если первый запрос однозначно отклонён с 413 или 415, доступно «Выбрать другой файл»: после очистки собственной копии приложение возвращается к выбору без автоматической отправки.

«Обновить статус» запрашивает сервер и сохраняет уже отображённый результат, если сервер вернул устаревшее состояние. После обычного запуска приложения и возвращения из фона выполняется восстановление через GET; POST и DELETE самопроизвольно не повторяются. Уже подтверждённое удаление допускает завершение локальной очистки без сети.

## Подключение к mock

Из корня проекта в отдельном терминале:

```sh
npm run mock
```

Клиент по умолчанию использует `http://127.0.0.1:8787`. iOS Simulator обращается к loopback Mac. Для запущенного Android-эмулятора:

```sh
adb reverse tcp:8787 tcp:8787
```

Адрес задаётся переменной `EXPO_PUBLIC_IMPORT_API_URL` до запуска Metro. Например, для явно выбранного адреса компьютера в локальной сети:

```sh
EXPO_PUBLIC_IMPORT_API_URL=http://192.168.1.10:8787 npm start
```

Это публичная конфигурация клиента, не место для секретов. Для физического устройства потребуется также запустить mock на выбранном LAN-интерфейсе согласно инструкции комплекта. Не открывать тестовый API в интернет. Выбор и локальная проверка файла работают без запущенного mock.

## Ответственность модулей

| Модуль внутри фичи | Ответственность |
| --- | --- |
| `api/importApi.ts` | POST настоящих байтов, GET по ключу и ID, DELETE с ключом, проверка ответов, timeout и безопасные ошибки |
| `lib/importStorage.ts` | Связь файлового журнала с Expo FileSystem и приватным каталогом Documents |
| `lib/importStorageJournal.ts` | Проверка схемы и неизменности ключа удаления, последовательные снимки, маркер очистки и удаление оставшихся файлов |
| `model/importOperation.ts` | Сохранение до POST и DELETE, переходы, повтор, polling, ревизии, поздние ответы и новый импорт |
| `model/useStatementImport.ts` | `expo/fetch`, `File`, UUID, React и события `AppState`; один координатор на процесс |
| `ui/StatementImportScreen.tsx`, `ui/ImportResult.tsx` | Подтверждения отправки и удаления, состояния и ошибки, результат, подробности и повтор |

Модель получает API, хранилище, генератор ключа и планировщик через зависимости. Она проверяется без Expo и устройства. UI вызывает действия hook; HTTP и файловые операции в компонентах не выполняются.

## Сохранение до POST

Неподтверждённый выбор остаётся в cache и очищается по правилам [выбора файлов](file-selection.md). При подтверждении выполняется следующая последовательность:

1. Генерируется UUID v4 через уже установленный Expo.
2. Проверенная cache-копия копируется в приватный `Paths.document/statement-import-operation/payload-<key>.bin`. Передача исходного документа или удаление его provider URI не выполняются. Размер постоянной копии сверяется с проверенным размером выбора.
3. Записывается снимок операции: версия схемы, ключ, сведения о копии, пустой checkpoint сервера и `submission=prepared`.
4. Непосредственно перед POST сохраняется `submission=pending`. Только после завершения этой записи разрешается запрос. Cache-копия выбора освобождается отдельно от постоянной копии.

В снимке хранится относительное имя `payload`, а не абсолютный URI контейнера приложения. При загрузке путь строится от текущего Documents. Это позволяет восстановить операцию при изменении пути sandbox, например после обновления приложения в симуляторе.

Журнал пишет новый `state-<номер>.tmp`, затем переименовывает его в новый `state-<номер>.json`, не перезаписывая предыдущий commit. Сохранения выполняются последовательно. Незавершённые `.tmp` не считаются операцией; после успешного commit или загрузки удаляются ненужные временные файлы, брошенные payload и старые снимки. Пока нужен файл, сохраняются два последних снимка; после освобождения файла остаётся один актуальный снимок без его имени. Неудачная фоновая очистка повторяется при следующих действиях с журналом.

Повреждённый последний commit вызывает ошибку восстановления. Приложение не трактует его как пустое хранилище и не создаёт новый ключ. Ошибка сохранения до POST останавливает отправку; повтор сначала перечитывает журнал. Если файл пропал, сохранённый ключ всё равно позволяет найти уже принятый импорт.

## Передача и источник результата

`POST /imports` получает неизменённые байты с `Content-Type: application/octet-stream`, `Idempotency-Key` и `X-File-Name`. Это не JSON, Base64 и не `multipart/form-data`. Имя в заголовке ограничено контрактом mock; Unicode и управляющие символы кодируются для передачи через HTTP-заголовки. Байты документа не преобразуются.

Нативный адаптер передаёт объект `File` в `expo/fetch`. В установленной версии `expo/fetch` преобразует содержимое в массив байтов в JS-памяти размером до 10 МиБ после предварительной проверки файла. Это не потоковый upload; общий расход памяти с учётом копий и нативного запроса может быть больше размера файла. При выборе файла по-прежнему читается только префикс до 8 КиБ.

HTTP-клиент проверяет схему ответа, допустимые статусы и ревизии, идентичность job при GET по ID, суммы, валюту и даты результата. Необработанные сетевые исключения и тело ошибки сервера не попадают в UI. Timeout запроса — 15 секунд. `202` с `queued` является квитанцией; затем GET получает актуальное состояние. Для `queued`, `processing` и `deleting` следующий опрос планируется через одну секунду после обработки ответа, без параллельных запросов модели.

После сохранения checkpoint с ID job постоянная копия байтов удаляется: дальнейшее восстановление использует GET. Затем сохраняется снимок без сведений о файле. Если приложение завершилось между этими действиями, известный ID позволяет продолжить без повторной передачи. Ошибка очистки показывается пользователю и допускает повторную проверку.

## Потерянный ответ и перезапуск

| Ситуация | Действие клиента |
| --- | --- |
| Соединение оборвалось после POST | Искать job через `GET /imports/by-key/<key>`; не считать импорт неуспешным только по сетевой ошибке |
| Поиск по ключу нашёл job | Сохранить checkpoint, убрать собственную копию и продолжить GET по ID |
| Поиск вернул 404 | Сохранить ключ и файл. Это состояние на момент запроса, а не доказательство отсутствия незавершённого POST |
| Пользователь нажал «Повторить» | Сначала GET по сохранённому ID или ключу; при 404 по ключу допустим POST с прежними ключом и байтами |
| Обычный запуск или возврат из фона | Прочитать журнал и при необходимости выполнить GET. Если нужны повторные POST или DELETE, дождаться явного действия пользователя; уже подтверждённое удаление завершает только локальную очистку |
| Пришла более старая ревизия или откат статуса | Сохранить уже принятое состояние, не возвращать готовый результат в обработку |
| Завершился запрос предыдущей активации модели | Не применять его к текущему UI; после возврата восстановить состояние из журнала и сервера |

После ухода в фон новые опросы останавливаются. Уже начатый HTTP-запрос может завершиться на сервере; фоновый upload не гарантируется. После возвращения исход операции выясняется по сохранённому ключу или ID. После `ready` polling прекращается; ручное обновление и возвращение в приложение снова проверяют сервер.

## Окончательный отказ и замена файла

Сброс разрешён только после полученного ответа **первого** POST с 413 или 415, когда эта попытка началась из сохранённого `prepared`. Эти ответы mock выдаёт до создания job. Модель сохраняет `submission=rejected` и `rejectedStatus`; при перезапуске показывает отказ без нового POST. Кнопка «Выбрать другой файл» сначала удаляет собственный cache, затем через маркер очистки освобождает постоянную копию и журнал. При сбое очистки выбор новой выписки остаётся заблокированным и доступен повтор.

Для записей без `submission` сохраняется прежний неизвестный исход: миграция не превращает их в никогда не отправленные. `pending`, потерянный ответ, timeout и ответы 400, 408, 409, 429 или 5xx не дают права сбросить операцию. Даже 413/415 от повторной отправки после неизвестного исхода не стирают прежний ключ. В этих случаях остаётся восстановление через GET и повтор с теми же байтами. Это консервативное ограничение: доступность замены файла уступает защите от второго job.

После получения известного job поля `submission` и `rejectedStatus` убираются: дальнейший жизненный цикл определяется checkpoint сервера. Журнал запрещает возврат `pending` или старой записи в `prepared`, изменение окончательного отказа и его сброс до разрешённого состояния.

## Удаление и повтор после ошибки

Удалить можно операцию с известным job ID, в том числе ещё обрабатываемую. Два действия в UI разделены: «Удалить импорт» открывает подтверждение, «Подтвердить удаление» запускает модель. Отмена подтверждения не меняет сервер или сохранённую операцию.

Перед первым `DELETE /imports/<jobId>` модель создаёт отдельный UUID v4 и сохраняет его как необязательное поле `deleteKey` в существующем снимке. Старые записи без поля остаются читаемыми. Ключ удаления отличается от ключа создания и не может быть изменён или убран последующим сохранением этой операции. Если запись не удалась, DELETE не начинается; повтор сначала восстанавливает журнал.

DELETE отправляет `Idempotency-Key` и не передаёт файл повторно. Ответ `202/deleting` означает принятый запрос, а не завершённое удаление. Даже повторный `202/deleted` требует подтверждающего GET. Только GET со статусом `deleted` разрешает финальную локальную очистку и сообщение об успехе.

| Ситуация | Действие клиента |
| --- | --- |
| DELETE вернул `503`, произошёл timeout или потерян ответ | Показать незавершённое удаление и сохранить `deleteKey`; не утверждать, что импорт удалён |
| Пользователь нажал «Повторить удаление» | Сначала GET по ID. Если удаление ещё не началось, повторить DELETE с прежним ключом |
| GET вернул `deleting` | Продолжить polling; не отправлять дополнительный DELETE |
| GET вернул `deleted` | Сохранить terminal checkpoint, завершить локальную очистку, показать успех |
| Перезапуск во время удаления | Восстановить ключ и checkpoint, проверить GET. Если требуется ещё один DELETE, дождаться явного повтора |
| Сервер уже подтвердил удаление, очистка на устройстве завершилась ошибкой | Показать отдельную ошибку и «Повторить очистку»; новый импорт пока недоступен |
| Пришёл старый `ready` после `deleting` или `deleted` | Не возвращать результат: модель отклоняет откат статуса и ревизии, а завершённая операция не восстанавливается из старого снимка |

При проверке `delete_failure` переключают mock обратно в `happy` **без reset**, затем повторяют удаление. Иначе будет уничтожена операция, на которой проверяется повтор с тем же ключом.

## Завершённая очистка и новый импорт

После сохранённого `deleted` файловый адаптер очищает обе собственные cache-папки picker. Если очистка не удалась, checkpoint сохраняется для повтора, новый импорт заблокирован. Затем журнал записывает новый commit `{version: 1, cleared: true}`. Этот маркер не содержит ключей, имени файла, job ID или результата. Только после его сохранения удаляются старые снимки, временные записи и оставшиеся собственные payload. Пользовательский исходный документ не затрагивается.

Маркер остаётся последним commit, поэтому остановка процесса посреди очистки не возвращает старую операцию. Ошибки очистки на этом шаге не скрываются: `clear` и загрузка маркера повторяют удаление остатков и сообщают сбой, пока оно не завершилось. Позднее сохранение checkpoint старой операции поверх маркера запрещено.

После успешной очистки модель убирает результат из памяти и разрешает «Выбрать новую выписку». Новый выбор не отправляется автоматически; подтверждение создаёт другую операцию с новым ключом и заменяет маркер новым снимком. После обычного перезапуска уже очищенного приложения сразу доступен пустой экран выбора.

## Данные и ограничения этапа

Результат с описаниями списаний хранится только в памяти; после перезапуска он запрашивается заново. На диске остаются минимальный checkpoint и ключ. До подтверждения найденного job сохраняется копия для повторного POST; после освобождения файла старые снимки с его именем удаляются. Если очистка не удалась, она повторяется при следующем чтении или сохранении журнала. Приложение не логирует имя, URI, байты или позиции результата и не отправляет их в аналитику. Обязательное имя и байты передаются только выбранному API после подтверждения.

Одновременно поддерживается одна сохранённая операция. Следующую можно начать после завершённого удаления либо однозначного отказа первого POST, в обоих случаях — только после локальной очистки. Сброс mock во время незавершённой операции не является проверкой восстановления: он удаляет серверное состояние, на которое ссылается клиент.

Проверки API используют неизменённый `createMockServer` с отдельным временным state-файлом. Они не сбрасывают состояние работающего пользовательского mock. Команды из корня: `npm run typecheck`, `npm run test:mobile`, `npm run test:mock`. Результаты автоматических и нативных проверок фиксируются раздельно в [матрице приёмки](acceptance.md). iOS проверен от подготовленной сохранённой операции до отправки, результата и перезапуска, Android — восстановление по ключу. Полный путь выбор → подтверждение → результат ещё требует ручной проверки.
