# План реализации

Реализованы выбор и локальная проверка PDF/CSV, подтверждение отправки, сохранение до POST, сетевой импорт, результат, восстановление и асинхронное серверное удаление с повтором. После подтверждённого удаления и локальной очистки доступен новый импорт. Кандидат подтвердил ручной прогон и запись видео обеих платформ 2026-11-03. Далее — оставшиеся проверки доступности, полная нативная сборка из чистого clone и передача материалов сдачи. Нормативные требования находятся в [описании задания](assignment.md), проверяемые условия — в [матрице приёмки](acceptance.md).

## Принятые решения

1. **React Native и TypeScript, Expo development build.** Это разрешено заданием. Используем локальные нативные сборки без EAS, аккаунта Expo и публикации. Expo Go и web не являются способом приёмки.
2. **Мобильный клиент в `mobile/`, выданный комплект отдельно.** Файлы `mobile-engineer-kit/` и исходный PDF сохраняются без изменений. Зависимости клиента устанавливаются отдельно от mock.
3. **Один сценарий с восстановлением.** Один экран поддерживает выбор, подтверждение, отправку, обработку и результат. Постоянная копия и журнал операции добавлены вместе с POST, чтобы повтор после сетевого сбоя использовал прежний ключ и файл.
4. **Feature-based архитектура.** `src/app` собирает приложение, `src/features/statement-import` владеет полным сценарием импорта. API, состояние, файлы, UI и тесты размещаем внутри фичи, а не в общих папках по техническим слоям. Правила и текущая структура — в [архитектуре](architecture.md).
5. **Нативные проекты генерирует Expo CNG.** `mobile/ios` и `mobile/android` получаем через prebuild; постоянные настройки храним в `app.json` и config plugins. Генерация проектов не считается нативной проверкой.

## Ответственность внутри фичи импорта

В `statement-import` есть экран и результат, файловый адаптер, валидатор, HTTP-клиент, журнал, модели выбора и операции и их тесты. Ниже — ответственность модулей этой фичи. Все части остаются рядом с бизнес-сценарием, а не становятся глобальными слоями проекта.

| Модуль фичи | Ответственность |
| --- | --- |
| `lib` | Picker, проверка размера и содержимого, cache-копия выбора, постоянная копия и журнал операции, очистка |
| `api` | Отправка байтов, получение job по ключу и ID, DELETE с сохранённым ключом, проверка ответов и сетевые ошибки |
| `model` | Выбор, отмена и замена; сохранение до POST и DELETE, ключи, ревизии, polling, восстановление, очистка и новый импорт |
| `ui` | Выбор, подтверждения отправки и удаления, состояния, ошибки, результат, подробности и повтор |

Тесты располагаем рядом с проверяемыми модулями. Восстановление и удаление используют ту же модель операции и не выделяются в независимые фичи. `shared` добавляем только для действительно общего переиспользуемого кода.

## Инварианты для реализации

- Сохранять случайный ключ и минимальное состояние до первого POST. Для повторной отправки сохранять тот же ключ и те же байты.
- Сетевой сбой после POST означает неизвестный исход операции. Сначала искать job по ключу; `404` в гонке не доказывает, что исходный POST не будет принят.
- После обычного relaunch получать актуальный статус, не отправлять файл самопроизвольно.
- Сохранять `pending` до POST; очистку отклонённого импорта разрешать только после однозначных 413/415 первой попытки. Старые записи, потерянный ответ и отказ повтора не дают права сбросить ключ.
- Ответ `202` на POST — начало операции. Источник актуального состояния — GET. Старые ревизии не должны откатывать UI.
- Ключ удаления создавать и сохранять до DELETE. После `503` разрешать повтор с прежним ключом. Завершение удаления подтверждать только по `deleted` из GET; `202` на DELETE не означает завершение.
- После удаления игнорировать запоздалые ответы старой операции, даже если они содержат результат.
- После подтверждённого удаления сохранить маркер очистки без данных операции до удаления старых снимков и payload. Ошибка очистки блокирует новый импорт и допускает повтор.
- Проверять размер до чтения содержимого в JS. Сейчас native picker сначала создаёт дисковую cache-копию; адаптер проверяет её фактический размер, отклоняет неизвестный/некорректный размер и читает только префикс до 8 КиБ. Не доверять одному расширению или MIME.
- Собственную временную копию сохранять только пока она нужна для подтверждения или восстановления отправки; очищать при завершении или отмене. Исходный пользовательский файл не удалять.
- В аналитику и crash-логи не передавать байты, имя файла и описания операций из выписки.

## Вопросы для следующего этапа

Передать записанные кандидатом видео iOS/Android вместе с репозиторием. Остаются крупный шрифт/небольшой экран и полная нативная сборка из чистого clone. Детальные доказательства ручных счётчиков и непроверенные инструментально сценарии не приравниваются к общему подтверждению успешного прогона; точный статус приведён в матрице приёмки.

Выбор и копии описаны в [выборе PDF/CSV](file-selection.md), постоянное хранение и сетевые переходы — в [операции импорта](import-operation.md). Нативные проверки конкретных файлов, отмены, очистки и реального перезапуска процесса фиксируются в матрице приёмки отдельно от тестов модели. Работа upload в фоне не гарантируется: после возврата приложение восстанавливает состояние через GET.
