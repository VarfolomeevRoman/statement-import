# Архитектура

Используем feature-based архитектуру: код группируется вокруг пользовательского сценария. Это небольшое приложение с одной фичей; отдельные слои и абстракции добавляем по необходимости, без полного набора слоёв Feature-Sliced Design.

## Текущая структура

```text
mobile/
  App.tsx
  ios/                          Сгенерированный проект Xcode
  android/                      Сгенерированный проект Gradle
  src/
    app/
      App.tsx
    features/
      statement-import/
        index.ts
        api/
          importApi.ts
          importApi.test.mjs
        lib/
          statementFileGateway.ts
          validateStatementFile.ts
          validateStatementFile.test.mjs
          importStorage.ts
          importStorageJournal.ts
          importStorageJournal.test.mjs
        model/
          statementFileSelection.ts
          statementFileSelection.test.mjs
          useStatementFile.ts
          importOperation.types.ts
          importOperation.ts
          importOperation.test.mjs
          useStatementImport.ts
        ui/
          StatementImportScreen.tsx
          ImportResult.tsx
```

`mobile/App.tsx` переэкспортирует корневой компонент. `src/app/App.tsx` собирает приложение: подключает `SafeAreaProvider`, настраивает `StatusBar` и отображает экран через публичный API фичи. `StatementImportScreen` показывает выбор файла, подтверждение, состояния операции, результат и безопасные ошибки; файловых и сетевых вызовов в экране нет.

## Границы фичи

`statement-import` владеет полным жизненным циклом одной операции: выбором и проверкой файла, подтверждением, отправкой, восстановлением после сбоя или перезапуска, результатом и подробностями, удалением и очисткой временной копии. Эти шаги используют общие ключи и состояние, поэтому остаются внутри одной фичи.

Сейчас внутри фичи реализованы:

- `lib/statementFileGateway.ts` — адаптер `expo-document-picker` и `expo-file-system`: системный диалог, собственная копия, фактический размер, ограниченное чтение и очистка.
- `lib/validateStatementFile.ts` — чистые проверки размера и формата; не зависит от React Native или Expo и тестируется в Node.
- `model/statementFileSelection.ts` — модель с внедряемым файловым gateway: один активный выбор, отмена, замена, очистка и отклонение запоздалых результатов.
- `model/useStatementFile.ts` — соединяет модель с нативным адаптером и React через `useSyncExternalStore`; активирует и освобождает выбор вместе с экраном.
- `api/importApi.ts` — внедряемый HTTP-клиент: отправка байтов, получение job по ключу и ID, DELETE с ключом идемпотентности, проверка схемы ответов, timeout и безопасные ошибки.
- `lib/importStorageJournal.ts` — последовательный журнал снимков операции с внедряемыми файловыми операциями, сохранённым ключом удаления и маркером завершённой очистки; `lib/importStorage.ts` подключает приватный каталог Documents через Expo FileSystem.
- `model/importOperation.ts` — сохранение до POST и DELETE, восстановление через GET, повтор с прежними ключами, polling, проверка ревизий и переход к новому импорту после удаления и очистки. Модель не зависит от React Native.
- `model/useStatementImport.ts` — соединяет модели с `expo/fetch`, `File`, генератором UUID и событиями `AppState`. Один координатор операции живёт на процесс и освобождает cache-копию после сохранения отдельной постоянной копии.
- `ui/StatementImportScreen.tsx` — отображение состояния и вызов действий hook, включая явные подтверждения отправки и удаления, повтор удаления и начало нового импорта. `ui/ImportResult.tsx` вычисляет сумму из полученных позиций и раскрывает подробности; после начала удаления результат скрывается.

Контракт gateway и тип выбранного файла принадлежат модели. Нативный адаптер реализует этот контракт, а модель получает его как зависимость и тестируется без устройства. Внешний публичный API фичи по-прежнему экспортирует только экран.

Тесты размещены рядом с валидатором, хранилищем, API и моделями; из корня запускаются через `npm run test:mobile`. HTTP-тесты обращаются к неизменённому mock с отдельным временным состоянием. Удаление и восстановление используют ту же модель операции; отдельной фичи для них нет. Инварианты и ограничения описаны в [операции импорта](import-operation.md) и [плане реализации](implementation-plan.md).

## Жизненный цикл выбранного файла

Системный picker делает приватную копию на диске с `copyToCacheDirectory: true`. Адаптер получает её фактический размер и читает не более 8 КиБ для проверки PDF/CSV, затем перемещает допустимый файл в `Paths.cache/statement-import-selections`. Отмена диалога сохраняет предыдущий выбор; успешная замена удаляет прежнюю копию; явная отмена и уход с экрана освобождают выбранную копию. При новом процессе старые cache-копии очищаются во время активации модели: неподтверждённый выбор не восстанавливается.

После подтверждения создаются случайный ключ и отдельная копия в `Paths.document/statement-import-operation`. Журнал сохраняет ключ, сведения для повторной передачи и относительное имя копии до первого POST. После сохранения найденного job копия удаляется; остаются ключ, ID, статус и ревизия. Позиции результата на диск не записываются и после перезапуска получаются через GET.

Эта схема решает временный доступ к iOS Files URL и Android `content://` через копирование средствами native picker. Cache остаётся расходным хранилищем выбора, а восстановление подтверждённой операции использует Documents. Подробности — в [выборе PDF/CSV](file-selection.md) и [импорте и восстановлении](import-operation.md).

## Правила зависимостей

Направление зависимостей: `app → features → shared`. Приложение собирает фичи и может использовать общие примитивы; фича не импортирует `app`, а `shared` не знает о фичах и предметной области импорта.

- Внешний код использует фичу через её `index.ts`. Например, `app/App.tsx` импортирует `StatementImportScreen` из `../features/statement-import`.
- Внутри фичи разрешены прямые относительные импорты её модулей. UI отображает состояние и вызывает действия; HTTP-запросы, хранение и переходы состояния не размещаем в компонентах экрана.
- Фичи не обращаются напрямую к внутренним модулям друг друга. Если появятся другие сценарии, их взаимодействие организует `app` через публичные API.
- `shared` создаём только при появлении действительно общего переиспользуемого кода. Специфичные для выписки проверки и типы остаются в `statement-import`.

Пока `shared` отсутствует, отдельной библиотеки состояния и навигации нет. Их выбор зависит от реализации сценария.

## Нативные проекты

Используем Expo development build и Continuous Native Generation. Папки `mobile/ios/` и `mobile/android/` создаёт `expo prebuild`; исходный шаблон их не содержит. Команда из корня проекта:

```sh
npm run prebuild -- --no-install
```

Нативные папки игнорируются Git. Источник постоянных настроек — `mobile/app.json`, зависимости и config plugins: чистый prebuild пересоздаёт проекты, поэтому ручные правки в сгенерированных файлах не сохранятся. Если понадобится поддерживать собственный нативный код вне этого процесса, решение о способе хранения проектов пересмотрим явно.

Оба проекта сгенерированы локально. 1 ноября 2026 года после добавления `expo-document-picker` и прямой зависимости `expo-file-system` обе нативные сборки собраны, установлены и запущены: iPhone 16 Plus Simulator / iOS 18.2 и Pixel 7 Pro Emulator / Android 17 (API 37, arm64). На iOS подтверждено открытие системного Files. Проверки выбора конкретных документов и полного сетевого сценария фиксируются отдельно; наличие реализации импорта не означает завершённую нативную приёмку. Android Studio Rabbit 2 / 2026.2.2 успешно синхронизирует проект.

Фактические результаты — в [матрице приёмки](acceptance.md), инструкции — в [диагностике iOS](ios-troubleshooting.md) и [диагностике Android](android-troubleshooting.md). Подробности генерации проектов: [Expo CNG](https://docs.expo.dev/workflow/continuous-native-generation/).
